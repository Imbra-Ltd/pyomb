# 360-Degree Audit — 2026-09-01

Third audit of this repository, run on the release branch for v0.5.0. It is
owed because that is a minor release; ADR-033 narrowed the obligation to minor
and major releases so that running the audit is the cheaper option than
writing a document declining it.

pyomb is a headless library, so this follows `360-headless` as both earlier
reports did: the Value and Discovery perspectives do not apply, and the
Quality perspective is re-projected into nine engineering dimensions, each
reviewed under its own restated lens.

The template prefers one isolated subagent per dimension. This pass ran
sequentially with the lens restated before each dimension, which the template
permits when parallel agents are not available. That is a weaker isolation and
is recorded here rather than left for a reader to infer.

Every finding below carries the command or file that demonstrates it. Nothing
is marked UNVERIFIED. Two candidate findings were dropped after checking, and
both are recorded under the dimension they belong to, because a dropped
finding is the part of an audit that is otherwise invisible.

The 2026-08-18 and 2026-08-29 reports are left exactly as written. Their
grades are observations of those dates rather than values to re-derive.

## Current bottleneck

**Code quality (B+) and CI/CD (B+)**, for the two reasons the previous audit
gave. Cognitive complexity is still ungated, and nothing enforces that the
release pull request merges before the others.

The previous headline is closed. Field-range checking was the one FAIL under
Protocol correctness in August, and #196 shipped it: every packet component
now declares the bounds the specification puts on its fields, and two methods
read them. That dimension moves from B+ to A-.

What remains is the same spread the last report described, one item shorter.
Each is bounded, tracked, and none blocks a release.

Cognitive complexity is the item to name plainly. It was a FAIL on
2026-08-18, a FAIL on 2026-08-29, and is a FAIL here. #149 has been open
throughout. Three audits reporting the same thing is evidence that nothing has
been spent on it, not that it is hard.

## Protocol correctness — Grade: A-

| # | Sub-dimension | Status | Finding | Reproduction |
| --- | --- | --- | --- | --- |
| 1 | Wire assertions | PASS | 120 bytes constants across 33 of 71 test files | Parsing each test module and counting `ast.Constant` nodes whose value is `bytes` |
| 2 | Checksum vectors | PASS | CRC values come from outside the library | `tests/test_rtu_crc.py` cites crccalc.com and the reference implementation in the Modbus over Serial Line specification |
| 3 | Type hierarchy | PASS | The Liskov freeze is still gone | Searching `pyproject.toml` for the quoted `"override"` error code returns nothing |
| 4 | Field ranges | PASS | The bounds are declared and queryable | A Read Holding Registers PDU with a quantity of `0x07D1` still serializes, and `violations()` now reports it against the `0x0001` to `0x007D` cap |
| 5 | Enumerated sets | FAIL | The Diagnostics sub-function code is unchecked | `ModbusRequestFC8(sub_func=0x00FF, subfunc_data=[0]).violations()` returns empty, where the specification enumerates the permitted codes in section 6.8.1. Tracked as #262 |

Sub-dimension 4 is the dimension's headline and the reason it moves up a
band. It was the one FAIL in August. Every bound now sits on the class
carrying the field, read from the bundled specifications rather than from
memory: quantities, the coil value set and the MEI type from the Application
Protocol, the protocol identifier from the Messaging Implementation Guide,
and the slave address range from PI-MBUS-300.

Sub-dimension 5 is the finding this pass adds, and it is a gap in the same
work rather than a regression. The constraint pass encoded three shapes --
a range, a fixed value, and a rule across fields. An enumerated set is a
fourth, `LIMITS` cannot express it, and no class uses one. Write Single Coil
has the same shape at two values and is handled by an override, which is the
pattern #262 would follow.

Sub-dimension 1 is counted the same way as the previous report, so the two
numbers are comparable: 118 across 32 of 65 files then, 120 across 33 of 71
now. The vector count grew by two while the file count grew by six, because
this release's new test modules assert behaviour rather than frames.

| # | Sub-dimension | Status | Finding | Reproduction |

| 2 | Licensing | PASS | MIT, declared in SPDX form, with the file present | The packaging config and the LICENSE file |
| 3 | Toolchain lock | PASS | `uv.lock` is current and something refreshes it | Last changed 2026-08-21; Dependabot is enrolled on the pip ecosystem weekly with `increase-if-necessary` |
| 4 | Disaster recovery | PASS | Rebuildable from the repository alone | Certificates are generated rather than stored, and there is no external state |

Unchanged. Sub-dimension 3 deserves one clarification a later audit would
otherwise re-derive: no open Dependabot pull request and a lock eleven days
old is the expected state rather than a stall. This project bounds its
dependencies instead of pinning them, and `increase-if-necessary` raises a
floor only when a release genuinely requires it, so silence means no floor
needed moving.

A library with no runtime dependencies cannot inherit a transitive
vulnerability, cannot break on someone else's release, and cannot be held
hostage by an unmaintained package. That remains the strongest single fact in
this dimension, and it is a deliberate constraint rather than an accident.
